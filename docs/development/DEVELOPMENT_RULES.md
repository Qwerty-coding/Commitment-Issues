# Purpose

This document defines the engineering standards, coding conventions, architectural boundaries, and development principles for MergeGraph AI.

Every contribution, whether written by a developer or generated by an AI assistant, must comply with these rules.

The objective is to keep the codebase consistent, maintainable, and aligned with the project's core philosophy.

---

# Core Philosophy

MergeGraph AI is built around one central objective:

> **Extract the smallest semantically complete context required for AI-assisted merge conflict resolution.**

Every implementation decision should support this objective.

If a feature does not improve semantic understanding, explainability, or token efficiency, it should not be included in the MVP.

---

# Architecture Rules

## Rule 1 — Respect Layer Boundaries

The project is divided into independent layers:

```
Frontend

↓

API

↓

Core Engine

↓

Git / Tree-sitter / AI
```

No layer may bypass another.

Example:

❌ Frontend calling Git directly

❌ Frontend calling Gemini directly

✔ Frontend calls REST API only

---

## Rule 2 — Single Responsibility

Each package must own exactly one responsibility.

Good example:

```
internal/git
internal/parser
internal/semantic
internal/context
internal/prompt
internal/graph
internal/report
```

Avoid utility packages that become "dumping grounds."

---

## Rule 3 — Semantic Graph is the Source of Truth

Every feature that needs code relationships should consume the Semantic Graph.

Do not duplicate dependency analysis elsewhere.

---

## Rule 4 — Static Analysis Before AI

Never send raw repository data directly to the AI.

Always:

```
Repository

↓

Semantic Analysis

↓

Conflict Scope

↓

Prompt Context

↓

AI
```

The AI should never determine relevance.

The backend determines relevance.

---

# Coding Standards

## Go

Follow standard Go formatting (`gofmt`).

Keep functions small and focused.

Prefer composition over inheritance.

Return explicit errors.

Avoid global state.

---

## React

Use functional components.

Use TypeScript if introduced in future.

Prefer reusable components.

Keep components focused on presentation.

Business logic belongs in hooks or services.

# Error Handling

Never panic for expected errors.

Return structured errors.

Example

```go
return fmt.Errorf("failed to parse %s: %w", file, err)
```

Frontend errors should be user-friendly.

Backend logs may contain technical details.

---

# Logging

Log only meaningful events.

Good examples:

- Repository loaded
- Parsing started
- Graph generated
- AI request sent
- Report exported

Avoid excessive debug logging in production.

---

# Performance Rules

Large repositories must remain usable.

Never:

- Parse every file repeatedly.
- Render the entire graph.
- Recompute unchanged data.

Prefer:

- Lazy loading.
- Incremental updates.
- Cached analysis.

---

# Graph Rules

The graph should never display every node by default.

Always use progressive disclosure.

Repository

↓

Folders

↓

Files

↓

Functions

↓

Variables

Graph rendering must remain responsive.

---

# AI Rules

The AI is an assistant.

It is not the decision-maker.

Requirements:

- Show prompt preview.
- Explain recommendations.
- Require user approval.
- Never modify repositories automatically.

---

# API Rules

All communication must occur through versioned REST endpoints.

Never expose internal parser structures.

Always return stable DTOs.

---

# UI Rules

The Semantic Explorer is the primary workspace.

The interface should prioritize:

- clarity
- explainability
- discoverability
- responsiveness

Avoid unnecessary visual complexity.

---

# Testing Rules

Every major module should have tests.

Required:

- Repository analysis
- Parser
- Semantic extraction
- Conflict scope
- Prompt generation
- API endpoints

---

# Documentation Rules

Every major feature must update:

- PRD (if scope changes)
- Architecture (if design changes)
- API Spec (if contract changes)
- Roadmap (if milestones change)

Documentation is part of the implementation.

---

# MVP Boundaries

The following are intentionally excluded from Version 1.0:

- Context scoring engine
- Graph neural networks
- Machine learning ranking
- Real-time collaboration
- IDE plugins
- GitHub App integration
- Background indexing
- Local LLM execution
- Incremental semantic caching

Do not add these features unless the MVP is complete.

---

# Code Review Checklist

Before merging a change, verify:

- Does it respect the architecture?
- Does it improve semantic understanding?
- Does it reduce unnecessary context?
- Does it introduce unnecessary complexity?
- Does it update documentation if required?
- Are tests passing?

If any answer is "No," reconsider the change.

---

# AI Contributor Instructions

When using an AI assistant to modify this project:

1. Read the relevant specification documents before making changes.
2. Preserve architectural boundaries.
3. Avoid unnecessary refactoring.
4. Keep changes small and focused.
5. Explain significant design decisions.
6. Update documentation when behavior changes.
7. Do not introduce experimental features into the MVP without approval.

AI should assist implementation, not redefine the architecture.

---

# Guiding Principle

Every feature should answer:

> Does this improve semantic understanding or reduce unnecessary AI context?

If not, it does not belong in the MVP.

---

# Summary

These rules ensure that MergeGraph AI evolves consistently, remains maintainable, and stays focused on its primary objective of explainable, token-efficient merge conflict analysis.
